# บริบทและสถาปัตยกรรมทั้งระบบ — TikTok Shop Fashion Intelligence (Classroom Demo)

เอกสารนี้อธิบายว่าแอปนี้คืออะไร ข้อมูลไหลอย่างไร ใครใช้หน้าไหน และแต่ละส่วนมีหลักฐานอยู่ที่ใด เหมาะสำหรับผู้ที่เพิ่งเปิดรีโปครั้งแรก

> ข้อมูลทั้งหมดเป็นข้อมูลสังเคราะห์เพื่อการศึกษา ไม่ใช่ข้อมูลจริง เอกสารนี้ไม่มีรหัสผ่านหรือคีย์ใด ๆ และห้ามเพิ่มลงในรีโป (รีโปเป็น Public)

## 1. โจทย์และเป้าหมาย

ร้านเสื้อผ้าจำลองส่งไฟล์ข้อมูลมาเดือนละชุด (10 เดือน: ม.ค.–ต.ค. 2569) เจ้าของร้านต้องการเห็นยอดขายและวางแผนเดือนถัดไป แต่ข้อมูลต้องผ่านการตรวจคุณภาพก่อนจึงเชื่อถือได้ ระบบจึงทำสามอย่าง:

1. **นำข้อมูลเข้าอย่างตรวจสอบได้** (Pipeline 5 ขั้น + ตรวจคุณภาพ + กู้คืนเมื่อผิด)
2. **ให้เจ้าของร้านใช้เฉพาะข้อมูลที่ Publish แล้ว** (Business Dashboard, Forecast, แผน)
3. **ให้ผู้ดูแลข้อมูลเห็นสถานะและแก้ปัญหาได้** (Data Operations)

และเพิ่มส่วน MLOps เพื่อเปรียบเทียบโมเดล ML กับวิธีมาตรฐานอย่างโปร่งใส

## 2. คำศัพท์ที่ใช้บ่อย

| คำ | ความหมาย |
| :--- | :--- |
| **ER1** | ฐานข้อมูลปฏิบัติการ (PostgreSQL บน Neon) ที่ข้อมูล Source ถูกนำเข้า |
| **ER2 / Warehouse** | ฐานข้อมูลวิเคราะห์ (DuckDB, Star Schema + Mart) ที่สร้างจาก Data Lake |
| **Data Lake** | ไฟล์ Parquet 3 ชั้น: Landing → Raw → Standardized |
| **Source Lock** | รายการ Hash (SHA-256) ที่อนุมัติของ ZIP ทั้ง 10 เดือน ใช้ตรวจว่าไฟล์ไม่ถูกแก้ |
| **DQ (Data Quality)** | การตรวจคุณภาพข้อมูล เช่น รหัสสินค้าต้องมีใน Master |
| **Publish** | เมื่อเดือนผ่านทั้ง 5 ขั้นและกระทบยอดตรงกัน ระบบบันทึก Snapshot ว่าเผยแพร่ได้ |
| **Staging** | ข้อมูลที่ยังประมวลผลหรือถูกบล็อก **ไม่นับ** เป็นข้อมูลที่ Publish แล้ว |
| **Official Forecast / Seal** | ค่าพยากรณ์ทางการของเดือนหนึ่ง เมื่อ Seal แล้วแก้ไม่ได้ |
| **Shadow Forecast** | ค่าพยากรณ์ของ ML ที่บันทึกไว้ก่อนรู้ยอดจริง เพื่อเทียบอย่างยุติธรรมภายหลัง |
| **Champion / Challenger** | Champion = Baseline ที่ Seal เป็น Official, Challenger = ML (Ridge) |
| **WAPE** | ความคลาดเคลื่อนรวม = Σ\|คาด − จริง\| ÷ Σ จริง |

## 3. ภาพรวมระบบ

```
Source ZIP รายเดือน (21 CSV) ── ตรวจ Hash กับ Source Lock
   ▼ ①
ER1 (Neon PostgreSQL) ── ถ้า DQ ไม่ผ่านจะหยุดที่นี่ → Review & Fix
   ▼ ②
Data Lake: Landing / Raw (Parquet)  ▼ ③ Standardized (Parquet)
   ▼ ④
ER2 / DuckDB Warehouse
   ▼ ⑤ Validate (กระทบยอด ER1 ↔ ER2) → Publish Snapshot
Dashboard: Business Owner · Data Operations · Forecast · Monitoring
```

## 4. การไหลของข้อมูลรายเดือน

- เดือนแรก (มกราคม) เป็น Initial Load เดือนต่อไปเป็น Incremental โดยรันได้ทีละเดือนตามลำดับ (ปุ่ม **Run This Month** รันเพียงเดือนเดียวแล้วหยุด)
- ตั้งแต่เดือน **มิถุนายน** ต้องมี Official Forecast ที่ Seal แล้วของเดือนนั้นก่อนจึงรันได้
- Run แต่ละครั้งมี Run ID, สถานะ และหลักฐานต่อขั้นตอน เก็บถาวรและดูย้อนหลังได้ รีเฟรชหน้าแล้วสถานะต้องเหมือนเดิม (ใช้ข้อมูลจากฐานข้อมูลเป็นหลัก ไม่ใช่สถานะในเบราว์เซอร์)
- ระบบกันการรันซ้อน (ล็อก) และส่งคำสั่งซ้ำได้อย่างปลอดภัย (Idempotent)

## 5. คุณภาพข้อมูลและการกู้คืน (กรณีเดือนมีนาคม)

เดือนมีนาคมใน Source ชุดสาธิตมีรายการสินค้าที่ใช้รหัส SKU ที่ไม่มีใน Master จึงใช้แสดงการกู้คืน:

1. ขั้น ① ตรวจพบ → Run ถูกทำเครื่องหมายว่า *Blocked by DQ* และ **ไม่ Publish**
2. หน้าเว็บแสดง **Review & Fix**: ระบุแถว ไฟล์ ค่าที่ผิด และตัวช่วยเลือก SKU ที่ถูกต้อง (ระบบไม่เลือกให้)
3. ผู้ใช้เลือกค่าที่ถูกต้อง กรอกผู้ยืนยัน เหตุผล และหลักฐานอ้างอิง ระบบบันทึกเป็นประวัติต่อท้าย (append-only)
4. **Revalidate** แล้ว **Resume** เพื่อรันต่อจนครบ 5 ขั้น และ Publish
5. เดือนที่ Publish ไปแล้วไม่ถูกแก้ย้อนหลัง

ดูขั้นตอนละเอียดที่ [DQ_RECOVERY_RUNBOOK_TH.md](DQ_RECOVERY_RUNBOOK_TH.md)

## 6. แดชบอร์ดสองบทบาท

**Dashboard 1 — Business Owner** (ภาพรวมธุรกิจ, คาดการณ์และวางแผน, คาดการณ์เทียบผลจริง)
ใช้เฉพาะเดือนที่ Publish แล้ว: KPI ยอดขาย/กำไร, แยกกลุ่มสินค้า 5 กลุ่ม (PG01–PG05), Forecast, แผน, Scenario

**Dashboard 2 — Data Operations** (เมนู *ทดสอบการนำเข้าข้อมูล* → *Data Operations Overview*)
ตอบคำถามของผู้ดูแลข้อมูลในที่เดียว: Pipeline ถึงไหน (Published N/10), ต้องทำอะไรต่อ (Next Action), สถานะ 5 ขั้นของเดือนที่สำคัญ, DQ และ Error, Warehouse พร้อมไหม (Snapshot, กระทบยอด), และสรุปความพร้อมของ ML

กติกาของแผงนี้: ใช้สถานะที่บันทึกในฐานข้อมูลจริง ถ้าอ่านไม่ได้แสดง `NOT VERIFIED` ไม่แสดงเป็น 0 หรือ "ผ่าน" ดู [DATA_OPERATIONS_TH.md](data_operations/DATA_OPERATIONS_TH.md)

การ์ด Source แสดงไฟล์/เวอร์ชัน/Hash ตามเดือนจาก Source Lock และค่าที่ Backend บันทึก แยกเป็น 3 สถานะ: ไฟล์ · Hash · ผลตรวจ DQ (ไฟล์ถูกต้องอาจมีข้อมูลข้างในที่ DQ ไม่ผ่านได้)

## 7. พยากรณ์ และแผน

- พยากรณ์ยอดขายสุทธิรายเดือนแยกกลุ่มสินค้า ผู้ใช้สร้างฉบับร่างได้หลายฉบับแล้ว **Seal** เป็น Official (ระบบปฏิเสธถ้าเดือนที่ Publish ขาดกลุ่มสินค้าใดกลุ่มหนึ่งใน 5 กลุ่ม)
- แผนมีหลายเวอร์ชัน ผูกกับ Official Forecast ของเดือนนั้น
- Scenario (what-if) อ้างอิงเฉพาะยอดของเดือนก่อนหน้าที่ Publish แล้ว

### 7.1 แผนกับ Forecast และ Actual: ความสัมพันธ์ที่ควรเข้าใจ

| ตัวเลข | มาจาก | เปลี่ยนตามแผนหรือไม่ |
| :--- | :--- | :--- |
| **Actual** | Source สังเคราะห์ที่ล็อก Hash ผ่าน Pipeline | ไม่ |
| **Official Forecast** | ประวัติเดือนที่ Publish แล้ว ล็อกด้วย Seal | ไม่ |
| **Scenario Net / กำไร (ผลของแผน)** | คำนวณจากออเดอร์เดือนก่อน (ปริมาณคงที่) พร้อมส่วนลด คูปอง Ads ที่เลือก | ใช่ (เป็นตัวแปรของแผน) |

- แผนบันทึกได้เฉพาะ **ก่อน** นำเข้าเดือนนั้น (กันเขียนแผนย้อนหลังหลังรู้ยอดจริง) และต้องมี Official Forecast ที่ Seal แล้ว
- Ads ที่เพิ่มในแผน **ไม่ทำให้ยอดขายเพิ่ม** ในการคำนวณ (ไม่มีโมเดลผลของ Ads) กระทบเฉพาะต้นทุนและกำไร ส่วนลด Campaign และคูปองกระทบยอดขายสุทธิ
- หลังรันเดือนนั้น หน้า “คาดการณ์เทียบผลจริง” เทียบแผนที่บันทึกกับยอดจริงแยกเป็น (1) ทำตามแผนไหม: Ads, Campaign, Voucher, Affiliate, ตัวอย่างฟรี (2) ผลที่ได้: ยอดรวม ยอดขายสุทธิ กำไร (3) เกณฑ์ 3 ข้อ ระบบระบุว่า **ยังไม่ยืนยันว่ามีการทำตามแผน**
- **ข้อจำกัด:** Forecast ทำนายก่อนมีแผน ถ้าเปลี่ยนแผนจริง ส่วนต่าง Forecast vs Actual จะรวมผลของแผนด้วย ไม่ใช่ความแม่นของโมเดลล้วน ๆ ส่วนการเทียบ ML กับ Baseline ยังยุติธรรม เพราะทั้งสองทำนายก่อนมีแผนและใช้ Actual ตัวเดียวกัน

## 8. MLOps และ Champion–Challenger

- **Feature Store แบบ Point-in-time:** เก็บ Feature เป็น Parquet ที่เขียนครั้งเดียว (write-once) ไม่ใช้ข้อมูลหลังวันตัดข้อมูล
- **ฝึกและตรวจ:** Ridge เทียบกับ Baseline ด้วย Walk-forward (ต้องมีเดือนขั้นต่ำก่อนประเมิน)
- **Shadow Forecast:** บันทึกค่าของ ML ก่อนรู้ยอดจริง แล้วประเมินอัตโนมัติเมื่อเดือนนั้น Publish
- **ระดับหลักฐาน:** < 3 เดือน Insufficient · 3–5 Preliminary · ≥ 6 Adequate
- **คำแนะนำ (Recommendation):** ขึ้น *RECOMMEND_REVIEW* เมื่อครบทุกเกณฑ์: มีข้อมูล ≥ 6 เดือน, WAPE สะสมของ ML ต่ำกว่า Baseline ≥ 2 จุด, ชนะอย่างน้อย 4 จาก 6 เดือนล่าสุด, และไม่แย่กว่าเกิน 5 จุดในแต่ละกลุ่มสินค้า เป็น **คำแนะนำเท่านั้น**
- **ไม่เปลี่ยน Official อัตโนมัติ** และไม่มีระบบอนุมัติ/ล็อกอิน (เป็น Demo)
- **แยกแหล่งที่มาของผล (data origin):** ผลจากข้อมูลสังเคราะห์ทดสอบกฎ ถูกติดป้ายและไม่ปะปนกับผลจริงของระบบ
- ในข้อมูลสาธิตที่มี ML ยังไม่ชนะ Baseline อย่างชัดเจน และหลักฐานอยู่ที่ระดับ Preliminary

## 9. ความปลอดภัยและขอบเขต

- คำสั่งที่เปลี่ยนข้อมูลผ่านตั๋วที่เซ็นและมีเวลาหมดอายุ และเช็กที่มาของคำขอ (ไม่ใช่ระบบยืนยันตัวตนผู้ใช้)
- Error ที่แสดงบนหน้าจอถูกกรองไม่ให้รั่วข้อมูลการเชื่อมต่อ
- ความลับ (รหัสฐานข้อมูล, คีย์ Storage) อยู่ใน Environment ของ Vercel เท่านั้น **ห้ามอยู่ในรีโป โน้ตบุ๊ก หรือเอกสาร**
- เป็น Demo เพื่อการเรียน ไม่ได้ทำ Production Hardening เต็มรูปแบบ

## 11. คำถามที่พบบ่อย

- **ทำไม Published ไม่เท่ากับ Pipeline สำเร็จ?** เดือนที่ DQ ไม่ผ่านหรือยังรันไม่ครบ ไม่ถูกนับ เพื่อไม่ให้ Dashboard ใช้ข้อมูลที่ยังไม่ผ่านการตรวจ
- **ML ชนะแล้วระบบสลับไปใช้ ML หรือไม่?** ไม่ ระบบแนะนำให้คนทบทวนเท่านั้น
- **ผลใน Colab ขึ้นบนเว็บไหม?** ไม่ ทั้งสองเป็นคนละระบบ
- **ตัวเลขขึ้น NOT VERIFIED แปลว่าอะไร?** ระบบอ่านสถานะหรือหลักฐานไม่ได้ ไม่ได้แปลว่าผ่านหรือไม่ผ่าน
